# Zeal PRD

## Context

Zealは、Bazelを使うSWE向けのLocal first GUIです。
Lensやk9sでKubernetesの見方を学べたように、日常の操作を通じてBazelに詳しい人の見方を身につけ、チームで共有できる体験を作ります。
Bazelに詳しい人が捉えている対象と関係を、GUIの構成と操作に反映します。

対象は、普段 `build`、`run`、`test` を使うものの、操作と仕組みがつながって見えていないSWEです。

市場の見立ては、monorepoの価値が浸透する中で、Bazelが有力な選択肢になることです。
既存製品はcloudのbuild runnerとそのUIが中心で、Bazelの見方を自然に学べる手段が少ない、という仮説があります。
cloud runnerを持たない人も手元のリポジトリから使える入口を作り、Bazelを選び、使いこなせる人を増やします。

## Usage scenarios

[UI mock](mock/)

### 1. 知らなかったtargetに気づく

起案者は、普段使うtargetに関連して、開発作業を補助するtargetが用意されていることを、人からの案内で初めて知りました。

GUIで普段使うtargetを開くと、関連targetの存在、用途、定義のつながりが見えます。
個別に案内されなくても使い始められ、別のtargetでも同じ見方で関連targetを見つけられます。

### 2. 自分のbuildとBazelの処理がつながる

起案者は日々Bazelを使いながら、中で何が起きているかを知らないまま使っていることに不安を感じています。

GUIでは普段のbuildから、定義を読むLoading、処理を組み立てるAnalysis、必要な出力を得るExecutionの流れを見ます。
今回実行した処理と、結果を再利用した処理の件数が分かり、自分のコマンドと内部の動きを結びつけられます。

### 3. targetを見つけて実行する

起案者は、使いたいtargetのlabelを正確に覚えておらず、CLIでは記憶と補完頼みで打っています。

GUIではfuzzy検索でtargetを見つけ、その場で `build` `test` `run` を実行できます。
ruleの型が使える操作を決めることを、実行のたびに確かめます。
実行はCLIと同じ記録として残ります。

### 4. 実行履歴から自分のbuildを振り返る

起案者は、buildが「遅い」「cacheが効いていない」と感じても、振り返る手段を持っていません。

GUIではRBEを使わない環境でも、実行がlocalの履歴として溜まります。
各実行のphaseの内訳、profile、実行と再利用の分布を見られます。
繰り返し実行する中で、自分の操作と結果の変化を結びつけられます。

### 5. 履歴の傾向を見る

起案者は、buildがだんだん遅くなっている気がしても、それを確かめる術を持っていません。

GUIではlocalに溜まった実行履歴を集計し、期間・コマンド・結果で絞って見せます。
実行回数、所要時間、実行と再利用の分布の推移が分かります。
チームの基盤を持たなくても、自分の履歴だけで傾向を説明できます。

## Milestones

試作に先立ち、公式ドキュメントと熟練者の知見から、GUIで伝える対象と関係を整理し、画面と操作の設計基準にします。
シナリオと試作の範囲は、整理した見方に応じて見直します。
一つのリポジトリで、targetの関係、buildの動き、実行と履歴、傾向の順に試します。
各段階で、利用者が設計基準とした見方を身につけられるかを確かめます。
他のリポジトリ・言語・ruleへの対応拡大は、その後に回します。

### M1：targetと周辺の関係が見える（シナリオ1）

cloud runnerなしで、手元のリポジトリのファイル、target、用途、定義、依存関係を見渡せる試作を作ります。
まず実際の関連targetを題材に、用途、定義、target間の関係を正しく示す情報が得られるか、補足説明が必要かを確かめます。

個別の案内を受けていないSWEが関連targetを見つけて使い、別のtargetでも用途と関係を説明できれば到達です。

### M2：自分のbuildを説明できる（シナリオ2）

同じリポジトリの一回のbuildで、phaseの流れと、実行したactionの時系列を見せます。
観測できない部分は不明と表示します。[Bazelの評価モデル](https://bazel.build/extending/concepts)

利用者がphaseの流れと、実行したaction、再利用の件数を説明できれば到達です。再利用は観測可能な範囲に限ります。

### M3：targetを見つけて実行できる（シナリオ3）

fuzzy検索、tree、pattern（`:all` / `:*` / `//...`）からtargetや対象セットを選び、ruleの型に応じた `build` `test` `run` を実行できる試作を作ります。

案内なしにtargetを見つけ、適切な操作を選んで実行できれば到達です。

### M4：実行履歴とprofileが見られる（シナリオ4）

GUIから起こした実行をlocalに記録し、phaseの内訳、所要時間、実行と再利用の内訳を振り返られる試作を作ります。
BEPやexecution log等、手元で観測できる記録に限定し、観測できない実行は履歴に詳細を持たないことを明示します。

利用者が過去の自分の実行を比較し、cacheの効きや遅さの理由を説明できれば到達です。

### M5：履歴の傾向が見られる（シナリオ5）

localの実行履歴を期間・コマンド・結果で絞り、回数・所要時間・実行と再利用の分布の推移を表示する試作を作ります。

利用者が「最近遅くなった」を自分の履歴で確認し、どのphaseやactionに効いているか当たりをつけられれば到達です。
