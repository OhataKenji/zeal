Zeal M1 — コンポーネント設計

m1-targets.md(何を作るか)に対する、実装レベルの構成説明。
対象読者: 設計書は読んだが「どのファイルが何をするか」がまだ頭に入っていない人。

0一語でいうと

「bazel query の XML を、構造を替えずに焼き直して、UI へ丸ごと置き換えで渡すパイプライン」。 途中に DB も差分同期も賢いキャッシュもない。bazel query の結果を一回だけ parse して Snapshot と呼ぶ不変構造を作り、できたら古いものと差し替える。UI はその差し替えイベントを受けて再描画するだけ。 複雑に見える部分(スレッド、pending、partial)はすべて「この一方向パイプラインを壊さないための補強」である。

図1 — 全データが通る道はこの一本だけ。label.rs は xml→snapshot 間の矢印を支える純粋関数群、 lib.rs は外からの操作(commands)を受ける玄関。バックエンドとフロントエンドの間に流れるのは 「完成した Snapshot を含む AppState」だけで、途中経過は一度も流れない。

1境界線 — Rust と Svelte の分業

このアプリで最も大事な線引きは 言語の境界ではなく責務の境界。

Rust 側だけがやる Svelte 側だけがやる
ファイルシステムを触る(workspace 検証・workspace.json)
プロセスを spawn する(bazel/bazelisk、open/xdg-open)
XML を parse する
label の正規化と edge/file 分類
「今何が起きているか」の唯一の真実(Core) 		描画と入力
tree の形を決める(階層化は view の都合)
どの target を選んでいるか
used by の逆引き(edges を見るだけ)

境界を越える物は4つだけ。app-state イベント(push)と、3つの command: open_workspace / refresh / open_location。 初期値だけ特別に get_state(pull)がある。 細かい問い合わせ API は意図的に存在しない。Snapshot は数 MB でも stringify→emit で十分速く、 「全部渡して UI 側で引く」ほうが API を増やすより単純になる。

2Rust 側コンポーネント

lib.rs玄関

  • 4つの command を登録:get_state, open_workspace, refresh, open_location
  • 起動時 setup: ログ plugin、Core を manage、保存済み workspace の再 open
  • expand_home: ~/... を展開(8行)

入 UI からの invoke → 出 Core への書き込み + ingest::request の発火

state.rs唯一の可変セル

  • Core { Mutex<CoreState> }: workspace, bazel, snapshot(Arc), last_error, ingest_running/pending
  • dto(): CoreState → シリアライズ可能な AppStateDto
  • emit(): app-state イベントとして webview へ push

変更があるたび全体を emit。部分更新という概念はない。

ingest.rs指揮者

  • request(): 入口。実行中なら ingest_pending=true を立てて即 return(合体/coalescing)。実行中でなければスレッドを立てる
  • スレッド内ループ: fetch() → snapshot 差替 or last_error 記録 → pending が立っていればもう一周 → 終了
  • fetch(): bazel query 子プロセスを spawn。stdout → parse スレッド、stderr → drain スレッド、本体は try_wait+300s タイムアウトを回す
  • Outcome: Ok / Partial(exit≠0 だが rule が取れた — --keep_going) / Failed(snapshot は温存)

入 workspace + bazel path → 出 Outcome。「同時に走る query は1つ」をここが保証する

xml.rsXML→RawRule

  • parse_rules → read_body → read_children の3段。XML のネストと同じ形のループ
  • <rule-input> は無視(暗黙依存が混ざる)。edge は「属性名つきの <label>」だけから
  • <rule-output> → outputs。location は file:line:col を分解
  • 途中で切れた XML はエラーにせず、読めた分だけ返す

入 bazel の stdout(BufRead)→ 出 Vec<RawRule>

label.rslabel の算数

  • canonical: //app → //app:app、@@x → @x、@@//p → //p
  • is_dep_attr: visibility・$暗黙属性・//... 名前を除外
  • is_select_key / is_external / label_to_path

状態を持たない純粋関数だけのモジュール。ここにロジックを集約したので parser と builder が薄い

snapshot.rsRawRule→Snapshot

  • targets: 全 rule を canonical label で正規化+重複除去+ソート
  • edges/files: label_attrs を見て、宛先が既知 target か @... なら edge、それ以外は file
  • files の role: 入力側は属性名(srcs/data/...)、出力側は固定で out
  • meta: fetchedAt + status(ok/partial)

「edge か file か」の分類はここで完結。UI は分類結果を見るだけ

workspace.rs環境の3役

  • is_workspace: MODULE.bazel / WORKSPACE の存在
  • resolve_bazel: PATH を自前で走査し bazelisk 優先で解決
  • save / load_saved: app_data_dir の workspace.json への読み書き(設計上、永続化するのは path だけ。snapshot は永続化しない)

3Svelte 側コンポーネント

state.svelte.ts受信口 + store

  • app: $state のただ一つの reactive store。中身は AppStateDto そのまま
  • init(): app-state を listen しつつ、初期値を get_state で pull
  • openWorkspace / refresh / openLocation: invoke の薄いラッパ

model.ts純粋 view-model

  • buildTree(snap): package のディレクトリ階層に rules と files を配る。file は「自身の dir に最長一致する package」の節へ、無ければ owner の節へ畳む
  • flatten(root, expanded): tree→行配列(表示はこれだけを見る)
  • relations(snap, label): 関係4行(deps/data/used by/files)。used by は edges を逆向きに引くだけ — Rust 側に逆辺は存在しない
  • displayLabel / displayPath: 同一 package なら :name に短縮

App.svelte骨格

  • toolbar: workspace 表示(クリックで再選択)、composer(target 入力+コマンド選択+Send ※実行は M3)、refresh ボタン
  • sidebar: targets / runs の独立スクロール pane + ドラッグ可能な境界線、各 pane は畳める
  • content: partial/stale の警告バナー、取り込み中表示、WorkspacePrompt、TargetView
  • select(): 選択は composer の target 欄にも同期 — 「現在の target」の single source of truth

Tree.svelte左ペイン

  • flatten の行を描画。dir 行は開閉、rule/file 行は select
  • SvelteSet で展開状態を保持。外部選択(関係行クリック等)時は祖先 dir を自動展開
  • file 行は → :owner 表示、クリックで先頭 owner の target へ遷移

TargetView.svelte右ペイン

  • ヘッダ: label + rule class badge + BUILD:line(クリックで open_location → OS 既定アプリ)
  • deps → / data → / used by ←: 各 entry が target 遷移リンク。既知でない label(external 等)はテキスト表示
  • files: 入力 path 列挙 + → 出力 path

4時系列 — 4つの流れ

A. 起動(保存済み workspace あり)

  1. main.tsinit(): listen 登録 → get_state で初期値取得
  2. lib.rssetup: workspace.json を読み、まだ workspace なら Core にセットして ingest::request
  3. ingest.rsスレッド: fetch() — bazel spawn、stdout を streaming parse
  4. snapshot.rsRawRule[] → Snapshot を build、Core の snapshot を Arc ごと差替
  5. state.rsemit → state.svelte.tsstore 更新 → UI 再描画

B. refresh(取り込み中に再度要求)

  1. ingest.rs実行中なので pending=true で即 return — 2つ目の bazel は走らない
  2. ingest.rs現行 fetch 完了 → snapshot 差替 → pending を見て もう一周だけ fetch(合体、無限ループしない)

C. 失敗

  1. ingest.rsexit≠0 で rule が1つも取れなければ Failed: snapshot は古いまま、last_error に要約(stderr 末尾)
  2. ingest.rsexit≠0 でも rule が取れていれば Partial: snapshot 更新 + status=partial(banner が出る)
  3. App.sveltesnapshot 無し & last_error あり → エラー文 + retry ボタン

D. 選択(バックエンドを一切越えない)

  1. Tree/TargetViewclick → select(label)
  2. model.tsrelations() が Snapshot の中だけで deps/data/used by/files を引く
  3. Tree.svelte選択先の祖先 dir を自動展開

関係行や BUILD へのジャンプに IPC は要らない。Snapshot が全情報を持つので「選ぶ」は純粋な UI 状態の話。

5なぜそうなっているか

問い 答え
snapshot 全置換でいいの? アトミックに「成功したらまるごと新しい世界」。部分更新・差分マージ・世代管理のコードが全部いらない。Arc<Snapshot> なので差替はポインタ書き換え、emit 時の clone も Vec のコピー1回
queue じゃなく pending flag? 要求を貯めても意味がない — 次に走る query は常に「最新の workspace」1種類しかない。なので flag 1つで「終わったらもう一度」が正確なモデル
edge/file 分類が Rust 側? 「target への参照か、ただのファイルか」は canonical 化と既知 label 集合がないと判定できない。UI に label 算数を持ち込むと二重実装になるので backend で完結させる
tree 構築が frontend 側? 逆に tree は「見せ方」の都合。Rust はフラットな targets/edges/files を渡し、階層化・最長 prefix 一致・展開状態は全部 view 側の関心ごと
<rule-input> を無視? rule-input はフラット化済みで属性名を失い、--noimplicit_deps を付けても暗黙依存が混ざる。edge は「属性名つきの <label>」だけから取ると決めたので、こちらは読む必要自体がない
stderr を別スレッドで drain? pipe は容量を超えると子プロセスが write ブロックで固まる。読むのはエラー要約のためで、本文は末尾 8KB だけ残す
workspace.json だけ永続化? 再開時に同じ workspace を自動で開くため。snapshot は起動ごとに query し直す(設計の非目標: snapshot の保存)
partial をわざわざ区別? --keep_going 付きなので「exit≠0 でも XML の大半は健全」が普通に起きる。Failed に潰すと使える snapshot を捨てることになるので、banner 付きの部分 snapshot として扱う
