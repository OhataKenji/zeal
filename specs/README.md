# Runtime state transitions

A workspace **path** owns outstanding Bazel discovery processes; a workspace
**object** owns what can appear in the UI. Leaving A and returning to A creates
a new object with the same path. The old read must not populate the new view,
but a launch in A must still wait for that read's process. A single
`loading` flag cannot represent both obligations.

## Run the models

Install a full Java runtime and download `tla2tools.jar` v1.7.4 from the
official [TLA+ tools release](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4).
The jar's SHA-256 is `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`.

From `specs/`, check a model with TLC and a fresh state directory:

```sh
java -cp /absolute/path/to/tla2tools.jar tlc2.TLC -metadir /absolute/path/to/temp-dir -config History.cfg History
```

Use a new, empty `-metadir` for each run. These are exhaustive finite-state
searches, not random simulations. Terminal states have an explicit quiescent
action where needed; deadlock checking is not disabled.

## Model index

Each model owns a different question. A transport reply is an event, not
an assumption that the request succeeds. Weak fairness (`WF`) is used only
where a progress property needs an eventual reply, release, or dispatch.
It does not guarantee that a real Bazel process, socket, or disk will respond.

No installed listener or new snapshot fetch after teardown.                                                                                                                                            |
| [Workspace](Workspace.tla)             | `session.ts`: `openWorkspace`, `applyState`, restore, dispose. Open replies carry both a revisioned snapshot and a request-owned selection.                         | Two paths, three request tokens and three revisions. A stale open cannot select its path; a newer snapshot can arrive on a stale reply. Once explicitly opened, do not restore, even on rejection.                                                                                                          |
| [Reader](Reader.tla)                   | `session.ts`: workspace info, target detail/phase, saved invocation detail. Empty or cached → loading → ready/failed; abandoning a read retains its previous cache. | One slot, with/without cache, temporarily ineligible or permanently replaced. No publication after retirement; failure does not discard a cached value. Fair settlement releases the slot.                                                                                                                  |

| [Launch](Launch.tla)                   | `trackDiscovery`, `dispatchStart`, `start`: submit, navigate, finish a discovery read, dispatch, resolve, dispose.                                                  | Two paths, two overlapping discovery reads and two launches. | [Modules](Modules.tla)                 | Native `ModulesOperation::acquire`/`Drop`: graph and explain compete for the same per-path guard. Mutual exclusion per path, no leaked permits; fair return of existing calls drains shutdown.                                                                                                                                                                                   |

A superseded explanation holds the busy slot but cannot publish even if the original key is selected again.                                                                                                                                                                     |
| [Receipt](Receipt.tla)                 | `Stream`, `Receipt`, `reserve_attempt`: reserve, append, supersede, flush, commit, replay and queue ACKs.                                                           | Two streams for one invocation, sequence numbers 1–3 (the smallest range exposing an interior hole). Only a current recording attempt can promote completeness; replay cannot change it. ACKs require a successfully saved contiguous range (`AckSeen`), **not** a successful build or even `last_message`. |

### Composition and subsystem models

The specs are not a single full-system product; `LaunchAdmission` is a
focused composition of the `Launch` and `Invocation` instances at the IPC
boundary. Each row pairs a model with the runtime owner it abstracts and the
deliberate bounds of its finite inventory — bounds on modeled process and
control transitions, not claims about unknown or undocumented state. Every
`.cfg` names the invariants and properties the check enforces.

| Model                                              | Runtime owner                                                                                                                                               | Deliberate bounds                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [LaunchAdmission](LaunchAdmission.tla)             | `Launch` UI `INSTANCE` composed with the `Invocation` core `INSTANCE` at the IPC boundary: submit → sent ≠ spawned → accept/reject → reply                  | Explicit instances of the actual UI/native modules; one job, one cached endpoint and one pending reply. `AcceptedByLiveReceiver`, `RejectedCannotFocus`.                                                                                                                                                                                   |
| [ReceiptRecovery](ReceiptRecovery.tla)             | `bes.rs`/`store` receipt across process restarts: reserve → flush → commit → replay → ACK, with crash returning offline                                     | One invocation, three attempts; normal EOF may seal or leave the receipt partial; SQLite commits are atomic and flushed files survive process exit — including a child exit between `finish_writer` and save; power loss is not modeled. `VisibleComplete`, `AckImpliesCommit`, `ReplayReadOnly`, `NoOrphanPromotion`.                     |
| [ShutdownJoin](ShutdownJoin.tla)                   | `runner.rs` spawn/interrupt/observe/release, `state.rs` `ProcessGroup::revoke`, `modules.rs` `ModulesOperation`: two reusable slots, one guard              | "Joined" means the map/set entries are gone, not that an OS thread joined or a child died; one collapsed exit clock; no signal delivery, PID reuse, panic, scheduler fairness or real time. `ExitResult`; `SignalOnlyOwned`, `AdmissionClosed`, `StopTimePreserved`, `TimeoutIsNotJoin`.                                                   |
| [StreamAdmission](StreamAdmission.tla)             | `bes.rs` `Receiver::admit`, `Stream` append/partial/finish, `receive_events` and the spawned ACK task; the permit is held through `send_acks`               | Three one-shot clients, two permits (native 32), at most two events, one buffered ACK; queueing, not remote delivery; idle/send timeouts are decisions; no payloads, sequence validation or persistence internals. `PermitAccounting`, `AckRange`; `CancellationKeepsPermit`, `AckAfterSave`, `FlushBeforeAck`.                            |
| [DiagnosticRetention](DiagnosticRetention.tla)     | `runner.rs` `remember_diagnostic` before guard drop; `lib.rs` history load/settle; `CoreState::diagnostics_for`                                             | Two sibling workspaces, three terminal lifetimes (two reuse an id, never concurrently), cache bound two (native 32), one in-flight history read; store results are inputs — no SQLite, pin/window or monotone saves; readable console assumed, no tail bytes or UI ordering. `BoundedRetention`; `NewestFirst`, `SettleExactly`.           |
| [StoreAdmission](StoreAdmission.tla)               | `store/database.rs` `Store::open` takes `ACCESS` before inspecting any root; one open and one representative write per client                               | `disk` records admission facts across seven shapes; no other process, crash or security proof. `GuardLifetime`, `OnlyValidatedUse`, `CommittedExactlyOnce`; `FreshOnly`, `RefuseExisting`, `AllReleased`.                                                                                                                                  |
| [BoundedProcess](BoundedProcess.tla)               | `bazel_output.rs` `run_bazel_bounded`: the cancel flag is sampled before spawn, not atomically; one absolute deadline shared by wait and readers            | The helper contract for `modules.rs` (operation flag) and `workspace.rs` (fresh false flag), not an assertion that info has a stop API; byte caps, OS scheduling and kill/wait duration are outside; "ok" is a status, not exit 0. `NoReaderLeak`, `CompleteOutput`, `SharedTimeout`; `PrecancelRefused`, `SignalOnlyUnreaped`, `Settles`. |
| [WorkspaceRegistration](WorkspaceRegistration.tla) | Native registry: `lib.rs` `open_workspace`/`restore_workspace`, `workspace.rs` `is_workspace`/`load_saved`/`save`, `scope.rs` `Scope::validated`            | Two roots plus an alias spelling, two normalized scopes, two git origins, bounded revisions — not the UI token/delivery protocol (`Workspace`). `PreferredRegistered`; `InvalidCannotPublish`, `CanonicalUpsert`, `RestoreOnlySaved`, `PreferenceCannotRollback`, `SavedPair`, `SnapshotProjection`.                                       |
| [ConsoleOutput](ConsoleOutput.tla)                 | One mounted `ConsoleView` and its append-only console file; timer and view callers compete for the single poll                                              | Units, not bytes or xterm cells; two models the 64 KiB cap and the file stops at four units; no fairness, EOF, write/resize errors or display-promise guarantee. `SinglePoll`, `ReadFromCommit`, `DisplayBacked`; `NoFabricatedProgress`, `DisposedSilent`, `RetryAtFailedOffset`.                                                         |

Verifies `SavedReadsOnlyWhenSettled`, `CompareRequiresReadyLeft`, `CompareTargetSettled`, and `ComparisonMountedOnlyOnCompareTab`.                                                                                                                           |

## What a successful run means

With TLC 2.19 (tools v1.7.4), all 31 configurations exhausted their
queues: 120,242 distinct states summed across the separate searches.
All seven negative controls below failed for their intended reason.
These counts describe this configuration set, not coverage percentages.

Seven single-transition mutants were checked locally as negative controls
against the same configurations; they are not committed and CI does not run
them. Each had to fail with its named property and TLC violation exit code:
lost history follow-up (`ServeQueued`), gap ACK (`AckSeen`), stale graph
callback (`NoStaleEffect`), stale query result (`NoStaleResult`), stale
console write (`QueueIntact`), detached launch focus (`SafeFocus`), superseded
receipt commit (`NoStaleCommit`). A parser error, timeout or successful mutant
is not a passing negative control.

TLC checks the named properties on all reachable states of **each configured
abstraction**. Paths and tokens stand for distinct identities; payloads,
numeric limits and timing have deliberately small representations. Repeating
an action is unbounded in the cyclic models, but the domains and number of
simultaneous owners are not. The models are not run as one Cartesian product.
They enumerate a finite inventory of the process and control transitions found
in source; that inventory cannot speak for state the source leaves
undocumented, and a clean run is not a universal detection or
production-coverage guarantee. There is no machine-checked refinement from
arbitrary Rust/TypeScript executions to these specifications. Keep the
implementation tests for that boundary, and update the model, configuration
and tests together when a transition changes.
